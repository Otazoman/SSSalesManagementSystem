### BUG-079 発注明細のボタンを押し損ねても、数量が空のまま入庫を確定できる

- 見つけた日: 2026-11-03(画面での確認。BUG-070 の確認の中で見つかった)
- 症状: 入庫画面で発注明細のボタン(「ITEM-3001 / 残10」など)を押さずに進めると、数量が空のまま入庫を確定できてしまう。
- 調査(2026-11-03): 数量が0以下の明細は、画面(明細の追加)・API(400)の両方で受け付けない。発注を選んでもボタンを押さずに品目を選ぶと、
  発注明細と紐づかずに確定できる(発注の残数量が消し込まれない)ことを指していると考えられる。
  BUG-071 の対応で、発注に同じ品目の明細が1つだけなら自動で紐づけるようにした。
- 要確認: これで足りるか。足りない場合の案: 発注を選んでいて発注明細と紐づかない明細がある時に、確定の前に警告を出す。
- 対応(2026-11-08。Staging に反映済み): 発注を選んでいて(発注から作った入荷指示を選んだ場合を含む)、発注明細と紐づかない明細が
  ある時は、確定の前に「発注の入荷済数量に数えられず、仕入の『発注から選択』で計上できない」ことを示して確かめる(品目名を表示)。
  マニュアル([inventory/receiving.md](inventory/receiving.md))に追記。テスト2件。

### REQ-001 添付ファイル(R2)と D1 の使用容量を確認できるようにする

- 内容: 添付ファイルが使用している容量と、D1 が消費している容量が分かるようにする。
- 表示する画面: R2 の容量は「R2ファイル管理」([admin/r2-explorer.md](admin/r2-explorer.md))、D1 の容量は「D1データ参照・編集」([admin/d1-explorer.md](admin/d1-explorer.md))。
- 要確認: 表示の単位(全体の合計だけか、フォルダ・表ごとか)。D1 のデータベース全体の大きさは Worker から取得できる範囲を調べる。
  Cloudflare の API から取得する場合は、API トークンなど設定の追加が必要になる可能性がある(相談のうえ決める)。
- 決定(2026-11-08): 総容量も表示する。
- 対応(2026-11-08):
  - D1: `GET /api/d1-explorer/usage`。D1 がクエリの結果に返す大きさ(`size_after`)を DB ごとに取得する(追加の設定は不要)。
    OTP DB も大きさだけ表示する。Staging のように複数のバインディングが1つの DB を共有する場合は、大きさとテーブルの一覧が同じものを
    同じ DB とみなし、総容量では1回だけ数える。画面を開いた時に表示する。
  - R2: `GET /api/r2-explorer/usage`。バケットごとに全ファイルを一覧して、ファイル数・大きさを合計する(R2 には使用量を返す API が無い)。
    時間がかかるため、「容量を計算」ボタンを押した時だけ計算する。一覧の取得は R2 の Class A の操作に数えられる(1回で最大1,000件)。
  - 共通の表示の部品 `_shared/ui/StorageUsagePanel.tsx`(GB まで表示)。マニュアル(R2ファイル管理・D1データ参照)に追記。テスト: バックエンド2件・画面3件。

### TSK-004 倉庫間移動(横持ち)が、出庫と入庫を別々に入力する作りで、つながっていない

- 見つけた日: 2026-11-08(ユーザーの質問「倉庫間を横持ちさせる場合はどう入力するか」から)
- 今の作り(2026-11-08 のコードで確認):
  - 移動元の倉庫で「出荷 > 出庫」に **移動先倉庫** を選んで確定する(移動元の在庫が減る)。移動先の倉庫で「入荷 > 入庫」に **移動元倉庫** を
    選んで確定する(移動先の在庫が増える)。出庫から入庫は作られず、2つの記録はつながっていない。
  - 得意先と移動先倉庫・仕入先と移動元倉庫は、どちらか一方しか指定できない。倉庫間移動では得意先・仕入先が入らないため、納品書は作られず、
    仕入計上の「対象検収」にも出ない(倉庫間移動としては正しい)。発注を選んだ入庫では移動元倉庫を選べない(BUG-078)。
  - 出荷指示・入荷指示(外部倉庫向け)には、倉庫間移動の指定が無い。
- 問題: 入庫の入力漏れに気づけない。輸送中の在庫が分からない。出庫と入庫の数量の食い違いを確かめられない。
- ユーザーの方向性(2026-11-08):
  - 倉庫間移動は、入庫・出庫とは分けた機能(画面・記録)にした方がよいかもしれない。
  - 出荷指示・入荷指示からも、倉庫間移動ができるようにした方がよいかもしれない(外部倉庫との横持ちのため)。
- 検討すること(案):
  1. 倉庫間移動の伝票(移動元・移動先・品目・数量・状態: 出庫済み/輸送中/入庫済み)を新しく持つか、今の出庫・入庫の記録のつながりで表すか。
  2. 移動元の出庫を確定したら「入庫待ち」とし、移動先で入庫する時にそこから選んで数量を消し込む(一部入庫・差異の扱い)。
  3. 外部倉庫が絡む場合(自社→外部・外部→自社・外部→外部)に、出荷指示・入荷指示をどう作るか(指示書の宛先・承認の流れ)。
  4. 在庫照会での輸送中の在庫の見え方、棚卸・在庫評価(会計)での扱い。
  5. 今ある倉庫間移動の記録(出庫の移動先倉庫・入庫の移動元倉庫)の移行。
- DB・画面・承認の流れの変更を含むため、設計を相談してから進める。
