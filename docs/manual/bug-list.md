#### 実行する AI への共通ルール

  この計画と食い違う場合は作業を止めて利用者に確認する。
- 利用者は別の場所でも開発しているため、作業の最初に `git pull` と `git status` を行う。コミット・プッシュは指示があるまで行わない。
- この計画が許可していること: 各項目の「変更内容」に書いた範囲の API の応答の変更・DB の列の追加・Cloudflare 設定(`wrangler.jsonc.example`)の変更。

  新しい migration を1つ足す。着手前に、足す列を利用者に報告する。
- 1項目の進め方:
  1. 「対象」のファイルを読み、書いてある現状が今のコードと合っているか確かめる(合わなければ報告して止まる)。
  2. 先に失敗するテストを書く(バックエンドは packages/backend の vitest、画面は packages/frontend の vitest)。
  3. 実装し、対象のテストと `npx tsc --noEmit` を通す。バックエンドのテスト全体は時間切れで落ちることがあるため、対象のテストファイルを指定して実行する。
  4. この一覧の該当の行の状態を `確認待ち` にする。画面の動きが変わる場合は docs/manual/ の該当ページも直す。
  5. 変更したファイルの一覧と、「確認方法」を実行した結果を報告する。
- 完了の条件: 各項目の「確認方法」がすべて通ること。Staging へのデプロイと実機での確認は利用者が行う。
  承認申請の種類を足す項目・申請される伝票やマスタの入力項目を変える項目では、承認プレビューの設定とそのテスト(BUG-089)の更新も完了の条件に含める。

### CPU時間の上限対策(PERF-00〜10)

原因(コードと実測で確認したこと):

| 処理 | 確認した内容 | 無料プランの上限 |
|---|---|---|
| PDF 生成(見積・発注書・請求書など10種類) | 日本語フォント(3.7MB)の埋め込みと文字の配置で、1枚あたり CPU 115〜215 ms(作業環境の Node で同じライブラリを実測。Workers 上の値は前後する) | 1リクエスト 10 ms |
| ログインのパスワード照合 | PBKDF2 10万回で CPU 20〜26 ms(同上)。安全のための回数で、減らせない | 1リクエスト 10 ms |
| 申請履歴 `GET /api/workflow-tasks/history` | ページ指定があっても、全ての履歴を取得し、申請1件ごとに内容の読み込み・承認者の解決を行ってから、最後に1ページ分を切り出している。DB への問い合わせ回数が申請の総数に比例する | D1 は1リクエスト 50 回まで |
| 承認待ち `GET /api/workflow-tasks/my-pending` | 全社の承認待ちを取得し、1件ごとに5〜8回の問い合わせをしてから自分の分を選んでいる | 同上 |
| `GET /api/auth/profile`(全画面で呼ぶ) | 会社設定(KV の同じキー)を26回読み、26回 JSON として解釈している | 10 ms |
| 全 API 共通の前処理 | 毎回 users の件数を数える問い合わせ(初期セットアップ用)と、セッションの検証を2〜3回行っている | — |
| OTP メール | 送信待ちの表に登録するだけで、実際の送信は1分ごとの定期処理。最大で約1分待つ | — |

軽い API まで同じ時刻にまとめて落ちているのは、Cloudflare が上限を「たまに超える分は見逃し、続けて超えると打ち切る」動きをするためと考えられる
(推測。PERF-01 で確かめる)。上限の値は Workers の制限・D1 の制限で 2026-11-10 に確認した。

### BUG-103 承認フローの画面で、仕入・入出庫・入荷/出荷指示の承認フローを作れない

- 見つけた日: 2026-11-15(REQ-018 の作業で気づき、ユーザーが不具合として登録を依頼)
- 調べた結果(コード): 承認フローの画面(`frontend/app/admin/approval-flows/_hooks/useApprovalFlow.ts`)は「対象申請種別」の選択肢を画面の一覧
  (`/api/permissions/screens` の業務・業務マスタ)から作る。承認の申請は申請の種類(targetType)と同じ名前の承認フローを探す(`workflow-engine/engine.ts` の startWorkflow)。
  登録されている申請の種類のうち、画面の一覧に無いのは purchase_recognitions(仕入。画面は purchase_receipts)・inventory_stock(入庫・出庫・品質区分変更・廃棄・返品)・
  inventory_instructions(入荷指示・出荷指示)の3つ(REQ-018 の3つは `app/workflow/_shared/approval-only-request-types.ts` で足し済み)。
  そのため、この3つは CSV 取込でしか承認フローを作れず、画面で作った承認フロー(例: 「仕入管理」= purchase_receipts)は申請に使われない。
- 補足(2026-11-15): 入荷・出荷の単位で決まるのは「承認を使うか」のスイッチ(会社設定)で、承認の流れ(承認フロー)は申請の種類が同じものしか使われない。
  入庫・出庫・廃棄・返品の申請は inventory_stock、指示書は inventory_instructions、仕入は purchase_recognitions のため、承認フローの画面で「入荷」「出荷」「仕入管理」を
  選んで作ったフローは使われず、スイッチを ON にすると「合致する有効な承認フローが定義されていません」で申請できない(承認フローのサンプル CSV はこの3つの種類で入れている)。
- 決まったこと(2026-11-15 ユーザー確認): 承認フローはメニュー単位にする。申請は、伝票を作るメニューの承認フローを使う。
  入荷=入庫・入荷実績・入荷指示(倉庫間移動の入庫を含む)、出荷=出庫・出荷実績・出荷指示(倉庫間移動の出庫を含む)、在庫・棚卸管理=棚卸・品質区分の変更・廃棄・返品、
  仕入管理=仕入、請求管理=請求・入金(請求への入金・単体入金)、支払管理=支払の消込。承認フローの画面の「入金(請求への入金)」などの専用の種類はなくす。
  同じメニューの中で伝票の種類ごとに承認者を変えたい時は、今の「分岐条件」(購買申請の前払と同じ仕組み)で伝票の種類を指定できるようにする。
  分岐条件を指定しないフローは、そのメニューの全ての伝票に使う。
- 対応(2026-11-15、今ある承認フローを移すことはユーザー確認済み):
  - 承認の申請は、アダプターの resolveFlowTarget で「伝票を作るメニュー」と「伝票の種類(documentKind)」を決め、そのメニューの承認フローを探す(engine.ts の startWorkflow)。
    documentKind は分岐条件に渡すため、同じメニューの中で伝票の種類ごとに承認者を変えられる(条件のあるフローを優先。条件の無いフローはメニューの全ての伝票に使う)。
    documentKind: 入荷 RECEIPT・RECEIPT_INSTRUCTION、出荷 SHIPMENT・SHIPMENT_INSTRUCTION、在庫・棚卸管理 AUDIT・RECLASSIFICATION・DISPOSAL・RETURN、
    請求管理 BILLING・PAYMENT_RECEIPT・CASH_RECEIPT、仕入管理 PURCHASE_RECOGNITION、支払管理 PAYMENT_DISBURSEMENT。
  - migration 0108(データの変更だけ): 旧い種類のフローをメニューの種類に移す。承認中の申請はフローの番号で進むため、元のフローはその場で書き換え、他のメニューの分は複製する。
    これまでの動き(入庫と入荷指示を別のフローで承認するなど)を保つため、移したフローには documentKind の分岐条件を付ける。
  - 承認フローの画面の「入金(請求への入金)」などの専用の種類は外した(承認タスク・申請履歴の種類名の表示には残す)。分岐条件の入力欄の説明に documentKind の値を書いた。
  - 承認フローのサンプル CSV をメニューの種類にした(28件のまま)。
  - 確認: flow-by-menu.test.ts(3件)。旧い種類でフローを作っていた在庫・支払・入金のテスト(6本)とフィクスチャ(inventory-approval)をメニューの種類に直した(意図した変更)。
    migration 0108 は SQLite で旧い種類のフローを入れて流し、書き換え・複製・分岐条件を確かめた。
- 直し方(案): approval-only-request-types.ts に3つの種類を足し、承認フローの選択肢・承認タスク/申請履歴の種類名に出す。
  あわせて、全ての申請の種類が画面の一覧かこの一覧のどちらかにあることを確かめるテストを足す(種類を足した時の漏れを防ぐ)。
